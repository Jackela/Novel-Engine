# 无机器校验清单

新契约里有些约束，**类型系统表达不了、门禁也验不到**。这张表把它们集中列出来，并区分两类：

- **已知缺口**：接受这个洞，靠别的手段兜，不打算在本轮填。写在这里是为了让后来者知道"这里不能只信类型"。
- **待办**：承诺会填，只是还没到那个阶段。写在这里是为了交付时不被误判为已完成。

两者的区别很重要。混为一谈会有两种后果：把缺口当待办，交付时被判未完成；把待办当缺口，漏洞就永远留在那里。

第三类状态是 **accepted（延后）**：承认这个洞，明确它**不**在本阶段补，并写清由哪个阶段的哪条验收承接。它与 accepted-risk 的区别只在一句话——accepted-risk 容易被读成"不修"，所以这里必须同时给出承接点；写不出承接点的，其实还是待办。

| # | 约束 | 类型为什么兜不住 | 现在靠什么 | 状态 |
|---|---|---|---|---|
| 1 | 全仓只有三处设置 `Retry-After`，**其中一个不走统一信封**：429 `RATE_LIMIT_EXCEEDED` 在 `auth_routes.ts:117` 直接 `reply.header`；409 `OPERATION_IN_FLIGHT` 六个抛出点里只有两个带（`job_history_service.ts:233`、`job_store_part.ts:289-294`）；503 `OPERATION_CAPACITY_EXCEEDED` 恒带 5。同为 503 的 `SERVICE_UNAVAILABLE` **不带**（持久层故障，`studio_schemas.ts:202-206` 用 `oneOf` 并列两种 503） | `retryAfterSeconds` 是可选数值，任何抛出点都能填，填错不报错；码表上也不该声明这个头（那会把"抛出点决定"压平成"码决定"） | **重建动作项**：429 那处必须改为走统一信封（`AppError.afterDelay`），否则限流响应失去头、客户端立刻重试并**反向放大压力**；反向断言至少覆盖**四分支**——非重试类 409、容量 422、`SERVICE_UNAVAILABLE` 503、带延迟但未传值的 409 | **accepted（延后）**：本次重建不新增专门测试，反向四分支由 generation 切片的 INV-40 验收承接。正向有旧测试 `job_retry_idempotency_contract.test.ts:97`，反向全仓零覆盖 |
| 2 | `defaultMessage` 与文档 §5 的转述保持一致 | 文案是 prose，逐字比对会逼文档复制每一句；类型层只保证它是 string | 文案指纹 `52a6eb27181b`（变更探测器，不是副本）；文档未写指纹行时门禁只打 note | **待办**：指纹行写入后由 note 转强制（脚本已支持，含"提到指纹但格式不可读即失败"的反向约束） |
| 3 | 三档超时的**值**填对（`firstByteMs` ≈ 30s、`idleMs` ≈ 60s、`deadlineMs` ≥ 180s） | 字段名按 arm 钉死，写错名字是编译错误；但把 60s 填进 `deadlineMs` 类型完全成立 | adapter 测试 + 规格 §1.4 的语义表 | **已知缺口**：值语义只能靠测试，端口类型不兜。adapter 实现时每个 arm 至少一条定时器用例 |
| 4 | `content_not_prose` **只有两个构造器**：净化闸门（"这不是正文"）与 `proposal_code_points`（正文超长）。adapter 永不产出 | 判别联合拦不住"谁构造"——任何拿到模块的地方都能抛 | 注释约定 + 代码审查 | **已知缺口**：若 adapter 图省事直接抛它，"不是正文"与"provider 坏了"会被混为一谈，失败归因指错方向。实现时在 adapter 层加 grep 级检查，**两个构造器都要禁**——只禁净化那个，超长路径仍会漏进来 |
| 5 | provider 无流式能力（`generateStructuredStreaming` 可选成员缺失）走 422 `INVALID_OPERATION`，不落 job | 可选成员的类型检查只在调用点，运行期才发现缺失 | 规格 §1.2 已列 | **已知缺口**：属"能力缺失"不是"内容不合法"，实现时注释要写清，避免被统一归进 `content_not_prose` |

## 每条失效时的上界

标「已知缺口」或「待办」还不够——结论会被后人当成「不重要」的同义词。写下上界，它才是一个**可复核的判断**：一旦有改动突破上界，读者能立刻发现前提失效，而不是继续沿用旧标签。

| # | 失效症状 | 上界 |
|---|---|---|
| 1 | 某准入点误传 `retryAfterSeconds`，响应多一个等待头 | 时长等于误传值，**不固定 1 秒**（本库的「默认延迟」并不统一：`OperationCapacityExceededError` 默认 5，keyed retry 显式传 1）。客户端多等 N 秒后重试**仍会失败**，只增延迟、不改错误类型。若哪天准入 409 演变成永久失败，这个上界失效，必须重判 |
| 2 | 文档 §5 的转述与契约文案脱节 | 不影响 wire，只影响读文档的人。指纹只覆盖 `defaultMessage` 本身；转述是散文，无法机器比对，所以上界止于「误导」 |
| 3 | 三档超时的值填错（如把 60s 填进 `deadlineMs`） | 最长表现是健康流被提前中断，或卡死的流拖到 180s 才断。不会丢数据，但会让「长文生成」在特定长度上稳定失败——这是能被用户复现的，不是静默的 |
| 4 | adapter 直接抛 `content_not_prose` | 归因错位：表面说「模型不听话」，实际是「provider 坏了」。上界是诊断方向错误，不会改变对外行为（两者都落 failed run） |
| 5 | 把「provider 无流式能力」归进 `content_not_prose` | 同上，且会让 422 的 `remedy` 指错（`reread` 而非 `configure`），客户端会重读资源而不是换 provider |

## 加一条的判据

新增条目时先回答：**这个东西出错时，是编译失败、测试失败，还是没人发现？**

前两种不必进这张表。只有第三种才需要，并且必须写清楚"靠什么兜"——写不出兜底手段的，说明它其实应该被做成有机器校验的形式，而不是进这张表。
