## 0. 执行摘要

**工程侧罕见地克制且真实生效；产品侧的核心可信度与外部验证严重缺失。**

- 正面基线：`arch` 门禁 0 违规、最大生产文件 331 行、234 个 server 测试文件 / 1421 用例与 130 个前端测试文件 / 702 用例全绿（合计约 3 分 56 秒）、无 TODO/FIXME 债务、备份/恢复与容器发布链实测可靠。
- 负面主线一：**中文用户的日常能力静默失效**——全文检索（FTS5 默认分词）、字数统计（按标点分段计）、导出（无中文字体/缩进/目录，EPUB 语言标成 en）、生成语言（提示词无语言跟随）。

- 风险侧：2 个可真实利用的安全问题（公网首启 Owner 抢占、信任代理下 XFF 限速绕过，均有实测）、1 个可复现的进程级事件循环冻结（453–970ms）、1 条静默丢字链（保存失败熔断 + 切换丢弃 + 无守卫）。

**修复工作单**：48 条 `DR-###` + 6 条 `DEC-###`（产品决策），见修复清单文档。

## 2. 分域结论

### 2.1 产品定位与伪需求

- 伪需求（无真实用户任务支撑的过度建模）主要集中在"元数据自我观察"：Job 机制（约 2,020 行，但同步执行、`GET /jobs/:jobId` 前端零调用）、Usage 成本（`estimated_cost` 死列、review 不记用量）、诊断导出（与 `doctor` 信息重复、无支持流程）、Snapshot 内部一致性（用户从未见过这个词）、Injection budget / Progressive disclosure / Canon（一个 4,000 字符 env 常量 + 概念再造，用户零控制面）。证据：`job_writes.ts:71`、`job_store_part.ts:114-117`、`diagnostics_routes.ts:18-60`、`lore_injection.ts:21,64-110`。
- 缺失的 table-stakes：接受前无 diff、生成粒度只能是整章、无查找/替换、无应用级撤销、无发布级导出、无实时字数、无敏感词自检；修订历史"只能恢复不能阅读"。
- 机会成本：spec 5,339 行中 36% 讲容量/原子性/生命周期，1,941 行；"文风/视角/人称"等写作核心在 spec 中 0 提及；前端为修订分页建了 628 行缓存，却没有查找/替换。
- 特殊风险：整本生成会对手写/导入/恢复的章节重新起草并自动接受（`wholeBookPlan.ts:8-19` 注释自认）。

### 2.2 用户可用性（中文长篇作者）

- 从零到"第一个字"要跨 11 道坎，其中 7 道与写作无关（Docker、终端、端口、环境变量），与"no development involved"的 README 承诺自相矛盾。
- 中文能力硬伤（均为静默错误，比崩溃更伤信任）：搜索实测全灭（"林黛玉/黛玉/宝玉"0 命中）、字数实测 22 字→3、DOCX 无中文字体/缩进/目录且标题重复、EPUB `dc:language=en`、mock 生成不认中文、清理器只删英文模板。
- 数据安全观感链：保存失败后无重试入口、切换文档丢弃 1.5s 内编辑、停止生成清空全部已生成文本、接受提案不可撤销、无密码找回路径。
- 文案与术语：首屏出现"自托管实例/API key/试用 provider"，provider 有三种中文译法；状态栏向用户展示 `修订 df65e3c4` 内部哈希；冲突文案"有人更改了这份文档"在单机场景归因错误。

### 2.3 架构与工程

- 生产代码 46,500 行（server 27,621 / frontend 18,879），测试 66,877 行（1.44×），OpenSpec 23,781 行；抽象数量合理，**过度的部分是过程与文档面**（测试:生产 1.44:1、规格:生产 0.51:1、23 个 campaign ledger）。
- 架构契约真实执行：`pnpm --dir server arch` 273 模块 / 1252 依赖 0 违规（2.5s）；四层边界与 `ai` 隔离规则生效。
- 唯一证实的技术风险：搜索路径同步执行 + `q` 无上限 + `MAX_MATCH_TOKENS=8` 且 bm25 需全匹配集打分 → 实测 8-token 停用词串在 200 章语料上冻结事件循环 452.9ms（更大语料 927–970ms）；恰发生在"边等 SSE 边搜索"的核心场景。
- 重写复盘：`python-final..HEAD` 209 提交 / +172k −47k；ADR-0002 质量高，better-sqlite3 是"SQLite 权威 + FTS5"硬约束下的必然选择；后悔的不是重写，而是重写后产能没有回到写作体验。
- 测试判定：有效断言（0 快照、0 skip、6,310 条 expect），是资产；但测试面 ≥ 生产面 1.44× 拖慢结构性演进；i18n 字典测试把英文文案按字节钉死是唯一明确该收敛的模式。

### 2.4 运维与安全（含实测）

- R1（High，实测）：公网/LAN 首启可被抢占 Owner——`POST /api/setup` 对无 Origin/Referer 客户端放行；容器实测第一个扫描器 201、真实作者 422 被永久锁死；无 CLI 自助恢复。
- R2（High，实测）：`SECURITY_TRUSTED_PROXIES` 下伪造 `X-Forwarded-For` 使登录限速归零（连续 16 次恶意登录零 429）；bcrypt cost 12 每次约 0.21s，可同时打满 CPU。
- R3–R6（Med）：每次启动写全量备份且永不清理（重启循环撑爆磁盘，restore 还需 2×库空间）；`doctor` 会迁移/备份/取锁且把错误塞进 `quick_check` 字段；`.env.example` 占位密钥可通过 production 守门；反代三陷阱（登录 DoS / TLS 下 setup 403 / trustProxy 缺失）。
- 已验证的可靠面：WAL 在线备份一致性、restore 三重拒绝路径不改动现库、SIGKILL 后数据完整、GHCR 镜像真实可拉可跑、首启 secret bootstrap 生效、日志不泄露敏感信息。

### 2.5 竞争与可持续性

- 竞品矩阵：Sudowrite/NovelAI/Novelcrafter/SillyTavern/Scrivener/Obsidian/国内工具对比后，Novel Engine 真正独有的两点：以"全项目不可变 snapshot"作为 review/export 的唯一读取单元；设定条目即文档本身（编辑即生效、无 resync）。
- 差异化真伪：resident context 是"确定性但浅"（每章 60 词截取，非摘要/非检索）；lorebook 机制可被 SillyTavern 超集平替，语义差异真实；自托管隐私只对"因保密/法务不放进云"的窄客群是 10x，且落盘为明文 SQLite；双语只是界面翻译，无网文特有能力。
- 可持续性：bus factor = 1（近 100 提交 100% 单作者；505 条历史无外部人类）；MIT 无护城河；贡献流程实为 agent 集群设计；发布节奏由内部战役驱动（21 天 5 个 minor，随后 17 天 0 release）。
- 存亡级风险：① 验证轮从未发生（访谈零执行）；② 单维护者 + 外发冻结；③ 品类被两端挤压（Novelcrafter BYOK ≈$4/mo；长上下文模型弱化上下文管理价值；国内平台占据中文网文生态）。

### 2.6 功能域 A：编辑器与写作核心

- 保存链：`error` 态熔断无重试（`useDocumentDraftAutosave.ts:83-90`）；切换/卸载丢弃 1.5s 内编辑且无 `beforeunload`（0 命中）；两个行为都被现有测试固化。
- 冲突链：只能"整体丢弃/整体覆盖"，无查看对方版本；无历史正文端点 → 覆盖后连阅读被覆盖文本都要靠又一次整体恢复。
- 版本链：历史列表无正文/无 diff/无确认；快照用户不可见且会阻止文档删除（409 无指引）。
- 结构链：卷 CRUD 前端方法零调用者、项目只有一个默认卷 → "Move to volume"永久不可达；项目删除后端已有、UI 无入口（0.3.0 同类问题换形态存活）。
- 深挖发现：revision 无界增长（每次自动保存整篇副本 + FTS 全量重写，无保留策略）；1 MiB 请求体硬墙对超长章节不可恢复（配合熔断成死局）。

### 2.7 功能域 B：AI 生成/审阅/上下文

- 流式是唯一在用的生成路径，但"永不重试"且中途失败双端丢弃已生成文本（服务端置空 + 前端清空），长章失败=全损+双倍计费。
- Review 两个硬伤：恒用 env 级 provider（默认 mock）而非项目所选；超时 30s（chapter 有 180s 地板，review 没有）→ 长稿必超时并白烧 3 次重试。
- 上下文组装：resident context 是确定性截取（60 词/章开头），非 CONTEXT.md 描述的"滚动摘要"；lorebook 预算与 progressive disclosure 与实现一致且测试充分（正面）。
- 韧性缺口：180s 绝对截止杀健康长流、无心跳帧、SSE 内错误帧被静默忽略；生成端点无幂等键（重复提交双份计费）；未配置 provider 报"不支持流式"误导。
- 用量：`estimated_cost` 死列；provider 未报 usage 时把 instruction 词数当 prompt tokens；无预算护栏。

### 2.8 功能域 C：搜索/导入/导出/备份

- 中文搜索实证（本报告最强证据）：DDL 无 tokenizer（`0000_init_persistence_core.sql:41`）；真实 inject 实测 `"林黛玉"/"黛玉"/"宝玉"` 全 0 命中、一篇中文小说命中 4/14；`Intl.Segmenter('zh')` 可解，trigram 对 2 字词仍失败；364 个测试文件中 CJK 搜索用例为 0。
- 无 FTS 重建/校验通道，doctor 不查索引 → 换 tokenizer 的任何修复都缺前置。
- 导出：三格式信息不对称（Markdown 丢章节标题、只有 chapter 入导出）；DOCX 无中文排版；EPUB 不合 EPUB 3（`dc:language=en`、缺 `dcterms:modified`）；PDF 无。
- 导入：hash 含绝对路径（改名/改内容即重复建项目）、标题丢失变 `Chapter N`、无前端入口（考古功能 + demo 用途）。
- 备份/恢复：机制扎实且文档一致（正面）；边角问题为 sidecar 残留、无备份后自检、明文说明。

### 2.9 功能域 D：平台功能与规格符合性

- 规格符合性抽查 12 条：多数满足；明确差距集中在写作统计（"words"定义对中文不成立、UTC 日界）、诊断导出（wire 缺 provider label、配置覆盖面窄于 spec）、lorebook wizard（"确认前零持久化"无对应断言）、路由清单与 `note` 类型等规格滞后。
- 会话：过期静默 401 跳转、无提示、丢草稿与位置；登出入口只在项目库。
- i18n：359 键 100% 对齐、文案质量高（正面）；但存在硬编码英文串（入口/网络层/契约层）、日期数字不随语言、编辑器 aria-label 语言陈旧；"界面双语、内容英文"。
- 设置面：只能改标题/描述/provider；model 不可见不可选；未配置 provider 可选中必然失败。

## 3. 交叉印证与张力

- **三方印证（同一事实被 3 个独立角色命中）**：中文搜索失效（用户 + 功能域 + 产品）、字数口径（用户 + 功能域 + 平台）、卷不可达（产品 + 功能域）、"保存/取消不可恢复"（用户 + 功能域）、投入配比失衡（架构 + 市场 + 产品）。
- **最大张力（本报告最重要的洞察）**：市场域判定"不可变修订 + snapshot"是唯一无竞品对应物的承重卖点；产品域判定该概念对用户不可见；功能域确认"历史正文都读不了、没有 diff"。三者合起来指向同一修复主题：**让版本能力可见可用（DR-010/011/012），比新增任何功能都更接近产品差异化**。
- **次级张力**：架构域称"导出不会拖垮进程"（实测 JSZip 主动让出事件循环），但同域的搜索冻结成立——风险不在导出而在搜索；运维域证实"每次启动备份"是磁盘放大器，而备份机制本身是正面资产（策略错，不是实现错）。
- **反直觉发现**：产品文档面向普通作者，但访谈筛选问卷把"不会装 Docker 的人"当作信号而非淘汰线——团队已知门槛却未收敛定位。
