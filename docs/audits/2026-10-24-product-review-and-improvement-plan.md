## 0. 一页结论

### 0.1 一句话判断

**这个产品已经"可信"，但还"不顺手"；而"不顺手"恰好落在它唯一无法被竞品替代的那条能力上。**

可信指数据不丢、版本不坏、部署能跑、备份能恢复——这一层已经做到行业上游水平，且有门禁和实测背书。不顺手指作者每次面对 AI 生成结果时，仍然只能做一次**盲签**：读一段纯文本，按接受，然后祈祷。

### 0.2 成熟度分层

| 维度 | 评级 | 依据 |
|---|---|---|
| 工程可靠性 | A | `arch` 门禁 273 模块 / 1252 依赖 0 违规；生产代码 58,424 行（server 31,889 / frontend 26,535），前端测试:生产 1.14:1；备份、恢复、崩溃恢复均有实测记录 |
| 写作核心体验 | C+ | 核心循环三处断点未修（见 §3）：接受无 diff、生成只有整章、接受不可撤销 |
| 激活与引导 | C | 新建项目只有标题与 premise 两个字段；无题材模板、无空态引导；首次价值时间从未实测 |
| 可发现性与分发 | D+ | 对外信号接近零（旧报告记录：6 star、0 外部人类提交）；GitHub Release 长期 draft |
| 商业可持续性 | 未定义 | MIT 无护城河、bus factor = 1、无定价与支持路径；roadmap 中无商业化条目 |

### 0.3 三条主结论

**结论一：可靠性投入的边际收益已经进入平台期，继续加厚的用户价值趋近于零。**

规格文档 114 条 requirement、约 23.3 万字符。按标题与内容归类，面向工程约束（容量、边界、原子性、契约、隔离、恢复）的 53 条占 15.4 万字符，约 66%；作者可直接感知的能力 25 条占 7.9 万字符，约 34%。单条最长的是 `Project-scoped export artifacts`（11,627 字符），比任何一条作者能力都长三倍以上。

这不是"过度工程"的指控。对一个把稿子放在本地、宣称数据归属的产品，可靠性是入场券，前一轮把 66% 的规格篇幅给它是正确的。问题在于入场券已经拿到，而"作者为什么每天打开它"这个问题还没有答案。

**结论二：产品的差异化承重点在版本能力，而版本能力目前只在"回看"路径可见，不在"决策"路径可见。**

不可变修订与快照，是这个产品相对 Sudowrite、NovelAI、Novelcrafter 唯一没有对应物的设计。但事实是：

- 提案接受前的预览是一段 `<pre>` 纯文本（`frontend/src/features/studio/components/StudioCopilotProposalPreview.tsx`），作者看不到"这段文字会替换掉我哪几句"；
- 修订历史里有行级 diff（`frontend/src/features/studio/historyLineDiff.ts`，含 LCS 退化保护），说明零件早就造好了，只是没接到提案路径上；
- 接受提案后没有撤销入口，回到旧版本要走历史面板再恢复。

也就是说，最能打的那张牌，被放在了作者做决定之后才翻开的地方。

**结论三：最大的单点风险不是功能缺口，是验证仍未发生。**

`docs/roadmap.md` 已经把"10 场访谈 + 冷启动实测"设为 0.9.0 的发布 gate，`docs/research/interview-kit.md` 把材料准备到了可以直接照读的程度。但截至本次审查，执行记录为零。如果验证失败，后面所有功能投入都可能建在一个不存在的需求上；如果验证成功，它会决定 P1 之后该做什么。**这件事不能排在功能之后，只能排在功能之前或与之并行。**

### 0.4 与既有评审的差异

| 2026-10-01 评审 | 本次审查 |
|---|---|
| 找缺陷（48 条 DR + 6 条 DEC） | 找结构（能力配比、决策路径、投入边际） |
| 结论："中文能力静默失效" | 结论："中文能力已修复，但决策路径仍然黑箱" |
| 建议：修 DR backlog | 建议：验证先行 + 把版本能力接进决策路径 |

## 2. 定位审查

### 2.1 产品现在有三种自我介绍

同一份仓库里并存三种说法，指向三个不同的用户：

| 出处 | 说法 | 隐含用户 |
|---|---|---|
| `README.md` 第 3 行 | "a self-hosted single-author novel writing IDE" | 能理解 IDE 这个词的人 |
| `README.zh-CN.md` 开篇（H1 定位句） | "跑在作者自己电脑上的 AI 小说工作室：稿子留在本地，模型由你选择——云端 API 或本地模型，无订阅、无按字计费" | 被订阅与 credits 困扰的长篇作者 |
| `docs/roadmap.md` | "the core loop is the product's load-bearing selling point" | 已经在用、正在评估核心循环质量的人 |

第一种是给开发者的，第二种是给作者的，第三种是给 Owner 自己的。三者不是互相矛盾，但**对外只有第一种被放在标题位**。英文 README 的第一行是整份仓库里权重最高的文案，它目前写的是分发方式（self-hosted）与形态（IDE），不是价值。

### 2.2 定位句的可信度检验

H1 句包含三个承诺：稿子留在本地、模型自选、无订阅无按字计费。逐条对照产品事实：

| 承诺 | 事实 | 判定 |
|---|---|---|
| 稿子留在本地 | SQLite 单文件、`data/` 目录、备份/恢复/导出齐全；但落盘为明文（旧报告已记录，README 未明说） | 成立，但需补一句明文说明，否则属于"承诺强于事实" |
| 模型自选 | `mock` / `dashscope` / `openai_compatible` 三种 provider；但项目设置里模型不可见不可选（旧报告 §2.9），实际只能改环境变量 | 部分成立，环境变量级而非产品级 |
| 无订阅无按字计费 | 产品本身不收费；但作者要付 provider 的 token 费，Usage 页按项目汇总 | 成立，但"无按字计费"容易被读成"不花钱"，访谈脚本里已经注意到这个概念对非技术作者的理解成本 |

第三条是真正的差异点，也是唯一能在访谈里被证伪的假设。`interview-kit.md` 的主画像就建立在这条上（"对 credits 黑盒有原话级抱怨"）。这个假设目前零验证。

### 2.3 竞争位势

按 2026-09-13 的竞品快照：

| 竞品 | 形态 | 价格锚 | 上下文机制 | 数据位置 |
|---|---|---|---|---|
| Sudowrite | web | $10–44/月（credits） | Story Bible | 云 |
| NovelAI | web | 免费层；$10/15/25 月 | Memory + Lorebook，端到端加密 | 云 |
| Novelcrafter | web | 21 天试用，约 $4/月起 | Codex 自动追踪 | 云，可导出 |
| SillyTavern | 自托管 | 免费（AGPL） | World Info / 角色卡 | 本地 |
| ChatGPT 工作流 | web | 订阅制 | Projects + 文件 | 云 |
| **Novel Engine** | 自托管 | 免费 + 自付 token | lore + resident context + 不可变快照 | 本地 |

两个真实差异，都不是"AI 写作"本身：

1. **快照作为审阅与导出的唯一读取单元**——导出的东西和审阅时的文本永远一致。竞品矩阵里没有对应物。
2. **设定条目就是文档本身**——编辑即生效，没有 Codex 那种"改了正文要回头 resync 设定"的二次劳动。

被挤压的两端也很清楚：Novelcrafter 用 BYOK 把"模型自选"打到约 $4/月，长上下文模型正在削弱"上下文工程"的溢价，国内平台占据中文网文的渠道生态。

结论：**自托管不是差异化，是被迫的形态选择；差异化在版本一致性与设定即文档。当前的对外文案（尤其是英文首行）没有说出这两点中的任何一点。**

### 2.4 定位结论

保留 H1 的中文表述作为作者面文案（它已经比原句好，且访谈里有 A/B 判读标准），但需要两处修正：

- 英文 README 首行从"形态 + 分发"改为"价值 + 形态"，与中文对齐；
- 补一句明文落盘说明，并把"模型自选"改成可核实的产品能力描述（当前是环境变量级，不能宣称产品级）。

不建议现在改定位句本身。访谈的 A/B 测试就是为这件事准备的，**先测再改**，否则是把未经证实的判断写成事实。

## 3. 核心循环审查

这一节是全文的重心。产品的核心循环是：**选章 → 下指令 → 读提案 → 接受 → 继续写**。四处断点里三处没修。

### 3.1 旅程与断点

| 跳 | 现状 | 判定 |
|---|---|---|
| 打开项目 → 选章 | 三栏布局、导航分组清晰、章节有序号与小节标题 | 完整 |
| 下指令 | 两个按钮（continue / rewrite）+ 一个指令输入框 | 可用但窄：只有两种操作意图 |
| 看提案 | 流式输出、可复制、有终态审计提示 | 完整 |
| **判断提案** | `<pre>` 纯文本预览，无差异对照 | **断点一** |
| **接受** | 整章替换，无粒度选择 | **断点二** |
| **接受后** | 无撤销，回退需进历史面板 | **断点三** |
| 继续写 | 自动保存、冲突检测、历史 | 完整 |

证据：

- `StudioCopilotProposalPreview.tsx` 的正文渲染是 `<pre>{proposal.result.proposal_markdown}</pre>`，注释自称 "read-only markdown preview"。
- `proposal_routes.ts` 的请求体只接受 `operation` 与 `instruction`，没有选区参数。
- 全前端检索 `undo` 零命中；`history` 面板提供 diff 与恢复，但不在接受路径上。

### 3.2 断点一：接受即盲签

作者看到的是一整段新文字，看不到它和自己现有手稿的差异。对一章 3,000 字的稿子，这意味着接受前要自己完成三件事：找出被改动的地方、判断改动是否比原文好、确认没有丢掉不该丢的句子。三件事都不便宜，所以实际行为大概率是**扫两眼就接受**（推断）。

这把"作者审阅 AI"降级成了"作者信任 AI"，而这恰恰是这个产品最不该让步的地方：它卖的是"你按接受之前它碰不到你的稿子"，但如果作者无法在几秒内判断该不该接受，这句话就只是流程上的安全，不是决策上的安全。

### 3.3 断点二：粒度只有整章

生成的最小单位是一章。想改一段，要么让模型重写整章（然后祈祷其余部分没变），要么自己动手。

对长稿作者，这个限制会随章节长度线性放大风险：章节越长，整章重写的期望损失越大，作者越不敢按。

### 3.4 断点三：接受不可逆

接受产生新 revision，旧 revision 还在，但入口在另一个面板。作者按下去的那一刻，没有"刚才那下我后悔了"的即时通道。

`POST /api/projects/:projectId/documents/:documentId/revisions/:revisionId/restore` 已经存在（`revision_routes.ts`），意味着**撤销在服务端是零成本的**，缺的只是一个 UI 入口和一次状态记录。

### 3.5 断点的共同根因

三处断点不是三个独立缺陷，是同一个设计取向的结果：**系统把"正确性"做在了存储层，把"可判断性"留给了作者。**

存储层做到了不可变、可追溯、可恢复；但从"提案存在"到"作者知道该不该接受"之间，产品没有提供任何认知支撑。行业内把它叫做 decision support，本产品的规格里没有这个概念。

### 3.6 一个被低估的机会

把 diff 接到提案路径上，不只是修一个易用性问题。它会顺带激活产品最独特的资产：

- 快照与修订的不可变性，从"回看时才用得上"变成"每次接受都在用"；
- 导出的确定性，从"技术保证"变成"作者能讲给别人听的故事"（我导出的这一版，就是我审过的那一版，逐字一致）；
- 竞品无法快速复制，因为它们的存储模型不是不可变的。

这是我在整份审查里唯一认为"投入产出比明显被低估"的一项。

## 4. 功能组合审查

### 4.1 九个 Inspector 标签的价值分层

`studioConstants.ts` 定义了 9 个标签：copilot、review、history、export、jobs、usage、stats、lore、settings。

按"作者多久用一次"分层：

| 层 | 标签 | 使用频率（推断） | 界面权重是否匹配 |
|---|---|---|---|
| 核心循环 | copilot、history | 每天 | 匹配 |
| 周期性支撑 | lore、review、export | 每周 | 匹配 |
| 配置 | settings | 一次 | 匹配 |
| **元数据自我观察** | **jobs、usage、stats** | **每月或从不** | **不匹配：占 1/3 标签位** |

`jobs` 尤其可疑：`CONTEXT.md` 明确写"proposal、review、export、lore-extract jobs 在其 HTTP 请求内同步执行"，也就是说这个标签展示的是**刚刚在同一个请求里已经结束的东西**。旧报告已经指出 `GET /jobs/:jobId` 前端零调用；现在有了 jobs 标签，但它的信息价值仍然接近"操作日志"。

`usage` 对目标画像（被 credits 困扰的作者）有明确价值，是定位句的证据面，应保留。`stats` 是留存钩子（写作 streak），有行为设计价值。三者不该同等对待。

### 4.2 Table stakes 对照

对"AI 辅助长篇写作"这个品类，作者会默认存在的能力：

| 能力 | 本产品 | 说明 |
|---|---|---|
| 查找替换 | 有 | Unreleased 补齐 |
| 快捷键保存 | 有 | Ctrl/Cmd+S |
| 基础排版命令 | 有 | 格式命令 |
| 深色模式 | 有 | 双主题 + 减少透明度降级 |
| 中英双语界面 | 有 | 359 键对齐（旧报告口径） |
| 修订历史 + diff | 有（仅历史面板） | 未接入提案路径 |
| **接受前 diff** | **无** | 见 §3.2 |
| **选区生成** | **无** | 见 §3.3 |
| **应用级撤销** | **无** | 见 §3.4 |
| **PDF 导出** | **无** | 投稿与打印场景缺口 |
| 章节字数目标 | 无 | 有统计，无目标 |
| 系列 / 多部曲管理 | 无 | project = 一本书 |
| 多人协作 | 无（明确非目标） | 与单作者定位一致 |

四项"无"里，前三项是同一主题的三个切面，第四项（PDF）是独立缺口。

### 4.3 功能过剩的四处

判断标准不是"有没有用"，而是"用户是否需要理解它"。

1. **Job 概念**：作者不需要知道什么是 job。它在 UI 上出现一次就是一次认知税。
2. **Usage 的逐模型明细**：对"这个月花了多少"有用，对"这个模型比那个便宜"意义有限（作者通常只配一个 provider）。
3. **诊断导出**：面向支持流程，但项目没有支持流程（无 issue 模板引导、无社区）。它是为"将来有用户"准备的，而用户还没来。
4. **Injection budget / Progressive disclosure / Canon**：三个概念在 `CONTEXT.md` 里有定义、在代码里有实现、在 UI 上几乎无控制面。旧报告已把这组归为"元数据自我观察"的伪需求，本次复核结论不变——但要注意，它们的**实现**是正确的，问题在于概念没有对作者暴露，也没有被作者需要。

### 4.4 能力缺口的优先级

按"缺失导致的损失"排序（推断）：

1. 接受前 diff —— 每次生成都在损失判断质量
2. 选区生成 —— 长章场景下限制生成能力的可用半径
3. 一键撤销 —— 每次接受都在积累"不敢按"的心理成本
4. PDF 导出 —— 交付环节的最后一步，缺失导致成品要出产品外加工
5. 系列管理 —— 三部曲作者的硬需求，但用户基数小

## 5. 激活与冷启动审查

### 5.1 新项目只有两个字段

`ProjectLibraryCreateForm.tsx` 的创建表单是 title + premise。提交后进入一个空项目：没有章节、没有大纲、没有人物。

对目标画像（正在写一部长篇的作者），这不构成问题——他有自己的稿子。对**第一次试用**的作者，这是空白页问题：一个写作工具最贵的时刻是"我打开它，然后不知道下一步做什么"。

`interview-kit.md` 的 TTFW 任务设计恰好绕开了这个问题：任务指令是"创建一个你自己的项目，写出第一段有 AI 参与的文字"，也就是说受访者被明确告知了下一步。真实用户没有这个指令。

### 5.2 TTFW 的结构性障碍

`interview-kit.md` 定了口径：产品内 ≤10 分钟、命令数 ≤3。产品内的路径是 T0 打开 → T1 登录 → T2 建项目 → T3 建章写字 → T4 下指令 → T5 接受。六段。

其中 T1 需要"创建 Owner 账户"，T2 只有两个字段，T3 需要点 Add 建章。**六段里有三段是纯配置动作，没有一段产生"这个东西对我有用"的感受。**第一个价值信号出现在 T5，也就是整个旅程的最后一步。

这是激活漏斗的典型形态：所有价值集中在末端，前面的每一步都是成本。可行的改法不是减少步骤数量（步骤已经很少），而是**把价值信号前移**——例如建项目时就让作者看到"这本书的设定已经变成 lore 条目"，或者在空态直接给一个可点的一步示例。

### 5.3 可发现性问题

九个标签、五个 section、三栏布局，全部信息密度都很高。旧报告记录过一类问题：功能存在但入口不可达（卷 CRUD 零调用者、项目删除无 UI 入口）。Unreleased 修了这两处，但**结构性风险还在**：功能增加的速度快于入口收敛的速度。

## 6. 度量体系审查

### 6.1 现状：零度量，且这是一个合理选择

全仓检索 `telemetry|analytics|posthog|sentry` 零命中。诊断导出明确写着 "no telemetry and no upload"。对一个宣称数据归属本地的产品，这是价值观一致的选择，不应改动。

但零度量带来一个副作用：**产品无法回答"这个功能有人用吗"**。旧报告能指出"卷 CRUD 零调用者"，靠的是静态代码检索，不是使用数据。当功能数量继续增长，静态检索会失效。

### 6.2 单人自托管产品该测什么

需要先说清楚一件事：这类产品的样本量是 1（Owner 本人）加上少量访谈对象，"北极星指标"的方法论在这里基本失效。周活、留存曲线、漏斗转化率都需要样本量支撑，一个自托管实例给不出来。

所以度量体系的目标不是增长仪表盘，是**诊断工具**：帮助 Owner 判断"我加的东西有没有被用"。

### 6.3 建议的三层度量

| 层 | 指标 | 数据来源 | 用途 |
|---|---|---|---|
| 决策质量 | 提案接受率、diff 查看率、撤销率、平均审阅时长 | 本地事件计数（不出本机） | 判断核心循环改造是否生效 |
| 系统健康 | 保存失败率、冲突率、流中断率、导出成功率 | 已有 job / 错误码统计 | 早于用户投诉发现问题 |
| 旅程效率 | TTFW 分段耗时、首章完成率 | 本地时间戳 | 验证 P1 冷启动改造 |

落地方式：复用现有 `stats` 聚合与 `diagnostics` 导出通道，扩成一个只读的"本地健康"面板，默认关闭、显式开启、永不联网。这与产品的价值观一致，也让 Owner 在访谈之外多一个客观参照。

需要提醒：**这套度量不能替代访谈**。它能告诉你"撤销按钮被点了 40 次"，不能告诉你"作者为什么不敢按接受"。

### 7.2 规格配比

| 类别 | 条数 | 字符数 | 占比 |
|---|---|---|---|
| 工程约束（容量、边界、原子性、契约、隔离、恢复） | 53 | 154,018 | 66% |

| 未归类 | 36 | — | — |

（未归类的 36 条多为流程性要求，如错误信封、会话契约、限流；归入工程侧会进一步抬高工程占比，此处保守处理。）

### 7.3 判断

这不是"重工程轻产品"的失衡。前一轮的结论是"投入配比失衡"，本次复核认为那个判断需要修正：**在一个数据安全承诺是核心卖点的产品上，把 66% 的规格给可靠性是正确的，且已经产生回报**（容器发布链、备份恢复、崩溃恢复都是可演示的资产）。

真正的问题是**边际**：可靠性投入的第 90 分位到第 99 分位，用户感知不到差别；而"接受前能不能看清差异"这种问题，用户每一次生成都会感知到。现在的投入结构仍然停在可靠性曲线的尾部。

一句话：不是方向错了，是**该换挡了**。

## 8. 改进计划

### 8.1 三条原则

1. **验证先于扩张。** 任何 P1 之后的功能，只有在访谈给出方向之后才立项。P0 的核心循环修复不受此限，因为它们已经在 roadmap 里、且不依赖用户偏好。
2. **每一分投入必须改变作者的一个决策。** 判断标准：改完之后，作者在某个具体时刻能做出一个改之前做不出的判断。做不到的，进 backlog 不进版本。
3. **不新增概念，只让已有能力可见。** 版本能力、快照、lore 都已经存在，缺的是显形。新增概念的成本是永久的，显形成本是一次性的。

### 8.2 分期总览

| 期 | 主题 | 周期（估算） | 发布 | 前置条件 |
|---|---|---|---|---|
| P0 | 验证 + 核心循环 | 4–6 周 | 0.9.0 | 无 |
| P1 | 冷启动与可发现性 | 4 周 | 0.9.x | P0 访谈结论 |
| P2 | 交付与出版 | 6 周 | 0.10.0 | P0 访谈结论 |
| P3 | 可持续性 | 持续 | — | Owner 决策 |

周期是单人投入的估算，不含等待访谈排期的时间。

### 8.3 P0：验证 + 核心循环（0.9.0 发布 gate）

#### P0-1 验证：先用模拟定假设，真实访谈延后

**为什么**：`docs/roadmap.md` 已经把用户验证设为 0.9.0 的发布 gate。材料（`docs/research/interview-kit.md`）已准备到可直接照读的程度，包括筛选问卷、45–60 分钟脚本、TTFW 计时段、A/B 定位句判读标准、速记表与综合表。

**当前状态（2026-10-24）**：Owner 决定暂不发出访谈邀请，改用七个模型角色做模拟评审。模拟已完成，产出见 [`docs/research/2026-10-24-simulated-interviews/10-synthesis.md`](../research/2026-10-24-simulated-interviews/10-synthesis.md)：七份角色材料、一轮交叉分析、十二条可检验假设。

**模拟改变了什么**：

- 接受前 diff 与一键撤销得到六个角色独立确认，性质从"体验优化"升级为"准入门槛"；
- **图形导入**从"考古功能"升为 P0（四份材料里三份说"没有这条不用看别的"）；
- 部分生成的理由从"效率"变成"核心循环形态"（六个角色里五个不用整章生成）；
- 系列管理从 P2 升到 P1，托管版从"选项"改为"不建议"；
- 新增五项此前完全漏掉的改进（见综合报告 §5.3）。

**模拟没有改变什么**：真实访谈仍然是发布 gate。模拟只能判断缺口在不在，不能判断缺口有多痛；它不产生留存信号，也不构成 gate 证据。

**下一步**：用综合报告 §6.3 的十二条假设重写访谈脚本，把十场开放式访谈改成"前 20 分钟开放式 + 后 25 分钟验证假设"，优先招三类人（非技术日更作者、有完稿在投稿的作者、系列作者），每类两到三人。

**验收**（访谈执行时）：
- 留存候选 ≥3，两周回访有记录；
- 定位句 A/B 有明确结论（H1 胜 / 原句胜 / 平局都算成功，"没有结论"算失败）；
- 十二条假设里至少八条被打分（成立 / 不成立 / 无结论）。

**工作量**：模拟已完成；访谈仍为 Owner 本人约 25–30 小时。

**风险与预案**：招募不到符合条件的作者 → 先降到 5 场并把"长篇"放宽到 3 万字，保留"每周至少一次"的频率线。

**这一项与 P0-2/3/4 并行，不串行。** 把它排在功能之后，等于用一个未验证的假设去指导 4–6 周开发；把它当作业交完再开发，则在等待期浪费掉一个可并行的窗口。

#### P0-2 接受前 diff

**为什么**：见 §3.2。这是唯一一项我认为投入产出比被明显低估的改动。

**做什么**：
- 把 `StudioCopilotProposalPreview` 的 `<pre>` 换成 diff 视图；
- **必须在句级做比较，不能直接用行级**。编辑器的换行是软换行（`useCodeMirrorEditor.ts` 启用 `EditorView.lineWrapping`），一段散文在存储里就是一个长行，行级 diff 会把"改一个词"渲染成整段删除加整段新增，噪声淹没信号。做法是按中文标点（。！？；）与换行切句，句级做 LCS，句内改动再用字符级高亮；
- `historyLineDiff.ts` 的类型与稳定 key 设计可以复用，比较单位要换成句子；现有 `MAX_LCS_CELLS`（250k）是为行级设的，3,000 字章节约 100–200 句，句级 LCS 在预算内；
- 接受按钮上方显示 `+N −M`（按句统计），提供"看全文"切换保留纯文本回退视图；
- 前端即可完成，不改后端契约：`proposal_markdown` 与当前草稿都在客户端。

**验收**：
- 任何提案都能出 diff，零例外；
- 一篇 3,000 字章节里只改一个词，diff 只高亮那一处，不出现整段标红（这是本条最关键的验收，行级实现会直接失败）；
- 3,000 字章节的 diff 渲染 <150ms；
- 无提案时零额外渲染成本；
- 同步更新 `openspec` 中 `Explicit AI proposals` 的 requirement 与前端契约测试。

**工作量**：5–8 人日（原估 3–5 人日，因句级切分与中文标点处理上调）。

**风险**：中文句读不一致（作者用空格、省略号、破折号断句）导致切分错位 → 切分失败时回退到行级并提示"按行显示"；英文段落需按句点切分，不能用中文标点表。

#### P0-3 一键撤销

**为什么**：见 §3.4。服务端能力已存在，缺 UI 入口。

**做什么**：
- 接受成功后记录 `baseRevisionId`，状态栏出现"已应用 · 撤销"，常驻 10 秒后收进历史面板的显式入口；
- 撤销调用已有 `POST .../revisions/:revisionId/restore`；
- 撤销本身产生新 revision，可再恢复（保持不可变语义，不做破坏性回滚）。

**验收**：
- 接受后 1 次点击回到接受前正文，逐字一致（用现有 revision diff 断言）；
- 撤销前先 flush 未保存草稿，避免与自动保存竞争；
- 撤销入口在历史面板永久可见，不只在状态栏一闪。

**工作量**：2–3 人日。

**风险**：撤销与自动保存竞态 → 复用现有 "flush on document switch" 的通道，已有先例。

#### P0-4 部分生成（选区/段落）

**为什么**：见 §3.3。这是三项里唯一有真实后端工作量的。

**做什么**：
- 提案请求体扩展 `target`（`whole_chapter` | `selection`）+ 选区文本或范围；
- prompt 组装的 resident context 分支：选区模式下只注入章节前文摘要与选区上下文，不注入整章；
- 编辑器选区 → "改写选中"入口；
- 冲突检测沿用 `baseRevisionId`，生成期间用户继续编辑则拒绝应用并提示。

**验收**：
- 选中 200 字生成，正文其余字节完全不变（用 revision 全文 diff 断言）；
- 选区跨段落、跨标点、含中文引号时不破句；
- 与整章生成共享同一套 job / usage / 幂等路径，不新增第二套管线。

**工作量**：8–12 人日（后端 prompt + 契约 + 前端选区 + 测试）。

**风险**：选区在生成期间失效（用户继续编辑）→ 明确提示"文档已变更，请重新生成"，不做静默合并。

#### P0-5 收口：按 roadmap 保留整本逐章确认

`docs/roadmap.md` 记录的第四项（整本生成只对空章自动生成，有作者文字的章节需逐章确认）已在 Unreleased 交付，**不需要重做**。计划里保留它，是为了防止后续重构把它丢掉——这是产品最容易被"效率优化"破坏的一条安全默认。

### 8.4 P1：冷启动与可发现性（访谈结论之后）

**前置**：P0-1 的痛点频次前 5 与画像结论。**在访谈之前不要定模板内容**，这是最容易被拍脑袋决定的地方。

候选动作（按访谈结果取舍，不全部做）：

| 动作 | 说明 | 验收 |
|---|---|---|
| 项目模板 | 2–3 个题材骨架（含卷/章/人物/世界的初值），内容由访谈中的真实工作流决定 | 新建项目到第一句 AI 参与文字 ≤5 步 |
| 空态三岔口 | 空白 Manuscript 给"从大纲开始 / 从第一章开始 / 导入旧稿"三条路 | 三条路各自可完成，不出现死路 |
| 价值信号前移 | 建项目后立刻展示"你的设定已变成 lore 条目"，把第一个价值信号从 T5 提到 T2 | TTFW 中位 ≤10 分钟 |
| Inspector 收敛 | jobs 并入 settings 或折叠为状态栏入口；usage 与 stats 合并为"统计" | 标签数 ≤7，核心循环仍在一级 |
| 术语清理 | 状态栏不再展示 `修订 df65e3c4` 这类内部哈希；单机场景的冲突文案改为"这份文档在另一个窗口被修改" | 用户可见文案零内部标识 |

`docs/roadmap.md` 的验证 gate 写明：若留存候选不达标，定位收窄而不是放宽。P1 的动作集合应当服从这个判定，而不是在判定之前全部开工。

### 8.5 P2：交付与出版（0.10.0）

| 动作 | 为什么 | 验收 |
|---|---|---|
| PDF 导出 | 投稿、打印、给编辑看稿的最后一公里；当前要出产品外加工 | 与 DOCX 同一快照、同一章节序；中文排版正确（字体、首行缩进、页边距、章节分页） |
| 导出模板 | 不同投稿渠道有格式要求 | 至少两套（通用投稿 / 打印稿），可保存为项目设置 |
| 系列管理 | 三部曲作者的硬需求，当前 project = 一本书 | 多项目可归入 series，导出时可合并；不做跨书 context 注入（避免范围蔓延） |

PDF 的技术路径由 Owner 决定（服务端渲染 / 前端打印 / 引入 PDF 库），本文只给验收标准，不指定实现。

### 8.6 P3：可持续性（owner 决策，本文只列选项）

这个问题不属于功能计划，但它是唯一能让前三个 P 有意义的前提。

| 选项 | 含义 | 代价 |
|---|---|---|
| A. 纯开源 + 赞助 | 接受 bus factor = 1，降低发布承诺，把项目定位为"作者自用的公开作品" | 增长与支持期望必须同步下调，README 要明说 |
| B. 托管版 | 云端一键实例，保留自托管作为免费档 | 与"数据留在本地"的核心承诺冲突，需要极清晰的产品分层 |
| C. 服务化 | 卖的是"帮你把稿子迁进来 + 配好 provider + 培训"，软件仍免费 | 需要销售与支持时间，与单人维护冲突 |

**不建议现在选。** 建议在 P0-1 访谈的付费意愿探针（kit §4 末段，参照物法）有数据之后再定。当前任何选择都是猜。

### 8.7 RICE 排序

Reach 为受影响的作者比例（推断），Impact 1–3，Confidence 为百分比，Effort 为人日。RICE = R × I × C / E。

| 排序 | 项目 | R | I | C | E | RICE | 期 |
|---|---|---|---|---|---|---|---|
| 1 | 接受前 diff | 1.0 | 3 | 0.9 | 4 | 0.68 | P0 |
| 2 | 一键撤销 | 1.0 | 2 | 0.9 | 3 | 0.60 | P0 |
| 3 | 验证轮（10 场） | 1.0 | 3 | 0.5 | 28h≈3.5d | 0.43 | P0 |
| 4 | 部分生成 | 0.6 | 3 | 0.7 | 10 | 0.13 | P0 |
| 5 | 空态三岔口 | 1.0 | 2 | 0.6 | 4 | 0.30 | P1 |
| 6 | 项目模板 | 0.8 | 2 | 0.5 | 5 | 0.16 | P1 |
| 7 | PDF 导出 | 0.4 | 2 | 0.8 | 6 | 0.11 | P2 |
| 8 | Inspector 收敛 | 1.0 | 1 | 0.8 | 3 | 0.27 | P1 |
| 9 | 系列管理 | 0.2 | 2 | 0.6 | 8 | 0.03 | P2 |

注意第 3 行：验证轮的 RICE 分数不高，因为它的 Effort 是 Owner 的时间而不是工程时间，且它不直接产出功能。**不要用这张表决定要不要做验证**——它的价值在于消除后面所有项目的假设风险，属于"期权"而非"功能"。RICE 是功能排序工具，不是决策工具。

### 8.8 明确不做（Non-goals）

写下来是为了防止范围蔓延，也是为了在访谈中被问到时有明确回答：

- **多人协作 / 评论 / 审稿流**：与单作者定位冲突，且会推翻"Owner 是唯一 principal"的鉴权模型。
- **云端 SaaS 版**：与"稿子留在本地"的核心承诺冲突。若要做，必须是独立产品线，不能作为本产品的部署选项。
- **provider 插件市场**：`docs/roadmap.md` 已明确否决（DEC-06），复核同意——DashScope 协议两次破坏兼容，抽象只为在用的 provider 存在。
- **移动端原生应用**：响应式布局已覆盖触屏（`Editor-first responsive and touch layout`），原生应用的成本与维护面不成比例。
- **全自动成书**：产品立场是"提案需作者显式接受"，全自动与这条冲突。
- **社区 / 作品发布**：会把产品从工具变成平台，用户基数不支持。

## 10. 本周可做的五件事

按"今天开始，本周能见到结果"筛：

1. **把 `StudioCopilotProposalPreview` 的 `<pre>` 换成 diff**（P0-2 的最小切片：只做行内 diff + `+N −M`，不做切换视图）。半天可见效果。
2. **在接受成功后加一个撤销入口**，直接调已有 restore 接口（P0-3 的最小切片）。一天。
3. **用十二条假设重写访谈脚本**（P0-1）。访谈本身延后，脚本要先就位——模拟已经把开放式问题收敛成可打分的假设（综合报告 §6.3），招到人就能开。
4. **给新建项目的空态加三条路**：从大纲开始 / 从第一章开始 / 导入旧稿。前两条是文案与路由，第三条先接一个"把 txt 或 docx 拖进来按章切分"的最小通道——模拟里四个角色把导入当准入门槛，完整实现是 P0-4，但空态入口可以今天就有。
5. **把 jobs 标签折叠进 settings**（P1 的收敛动作）。一小时，立刻减少一个认知税。
6. **给修订加命名与备注**。`document_revisions` 已有 `metadata_json` 列，不需要迁移；前端一个输入框，导出时带上。模拟里出版向作者的原话是"没有命名，三十多个修订我一个都指认不出"。

前三项加上第五、六项，都是"接线"性质，合计不到三天；第四项的第一条路径（导入的最小通道）是唯一需要新代码的，但可以先做 txt 切章，不做 docx。

第 1、2 项决定作者敢不敢按接受；第 4 项决定作者能不能进来；第 6 项决定作者能不能指认自己交出去的是哪一版。三件事分别对应"决策、准入、交付"，是模拟给出的最清晰的分组。
