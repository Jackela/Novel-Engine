# 模拟用户评审综合报告（2026-10-24）

## 0. 这份文档是什么，不是什么

**是什么**：七个独立角色对 Novel Engine 的一次结构化模拟评审。六个扮演目标与边缘用户，一个扮演竞品产品负责人。目的是找自评盲区、生成待验证假设、压力测试既有判断。

**不是什么**：不是用户验证。它不能证明任何关于真实作者的结论，不能替代 `docs/research/interview-kit.md` 的十场访谈，也不能作为 0.9.0 发布 gate 的证据。

这个区别不是免责声明，是使用方法：**模拟产出的每一条结论，都应被当作"待验证假设"而不是"发现"**。真实访谈要做的事，是给这些假设打分，而不是重新发明它们。

## 1. 方法

### 1.1 材料统一

七个角色读同一份事实基线（`00-fact-packet.md`），内容只陈述产品事实与竞品价格快照，不含价值判断。这样做的目的是防止角色各自想象一个产品来评价。

### 1.2 角色隔离

七个角色互不可见，各自独立输出。这是为了避免"第一个说话的人定调"——多 agent 评审最常见的失效模式是所有人都收敛到同一个显眼的结论上，看起来很一致，其实是回声。

### 1.3 任务脚本一致

每个角色都走同一条路径：读定位句 → 按首次使用路径走查 → 在指定节点停下来判断 → 给价值评分 → 列放弃理由 → 用参照物法定价 → 做定位句 A/B → 提三件必改 → 回答会不会用。

一致的任务脚本让七份材料可以横向比对；不一致的人物设定让比对有意义。

### 1.4 强制反迎合

每个角色的指令里都写了：不要礼貌性夸奖，不要写"用户体验有待提升"这类空话，必须给至少三条"我会放弃"的理由，必须标注确信度。反对派角色的任务被明确设为"说别人不好意思说的话"。

## 2. 六条硬限制

读下面的结论之前，先记住这五条。它们决定了哪些结论能用、哪些只能当参考。

**限制一：模型扮演的用户，会把"读到的功能描述"当成"用过的体验"。**

真实用户对"接受前没有 diff"的反应，来自他真的按了一次接受、然后发现改错了地方。模拟角色的反应，来自他读到这句话之后的推理。前者带情绪和具体损失，后者带逻辑。所以模拟能判断"这个缺口在不在"，不能判断"这个缺口有多痛"。

**限制二：七个角色共享同一个语言模型，存在系统性偏好。**

模型普遍高估"信息透明"和"可控性"的价值（所以 diff、撤销、版本这类东西会被一致看好），低估"习惯"和"懒得换"的力量（所以迁移成本容易被说轻）。真实作者里有一大批人明知道工具不好用，但就是不换。这一点模拟测不出来。

**限制三：角色不会真的卡住。**

真实用户卡在安装那一步，会关掉页面去做别的事，然后永远不回来。模拟角色会"卡住"，然后继续往下走完流程。所以模拟能列出卡点清单，不能给出流失率。

**限制四：付费意愿是编出来的。**

角色说的价格区间，是模型根据竞品价格和人物设定推出来的合理值，不是真实出价。参照物法能减少一部分失真，但不能消除。

**限制五：没有留存信号。**

访谈 kit 的核心判据是"两周后还在用"，模拟完全没有这个维度。任何看起来像"留存预测"的句子，都不该被当真。

**限制六：技术型角色的代码判断可能是错的，必须核查。**

技术型角色（K）会基于事实包推断实现细节，而事实包不写实现。他的四条判断我逐条核查过，一条错、两条对、一条证明产品做对了（见 §5.4）。这不是角色的失误，是模拟的固有风险：**越是具体的判断，越容易看起来可信，也越容易错**。任何关于"代码里怎么实现"的结论，在真实评审里都必须落到文件上。

## 3. 角色逐份结论

### 3.1 林筱（28，网文日更）— 2/10

装好并用上旧稿之后 6 分。会不会用：否。

她的第一道门不是产品，是 Docker。"这五条命令，我打在哪？Word 里吗？还是浏览器地址栏？"第二道门是旧稿：80 万字 380 章，产品没有导入，只能一章一章粘。

她不用 AI 写正文，理由不是技术，是生计：平台有 AI 检测，掉推荐位等于掉收入。但她说清了一件事——**她要的不是"写"，是"记"**。伏笔、人物关系、谁跟谁有过节，写到第 400 章还得记得第 312 章那块玉佩。lore 那套机制（关键词触发、只有稳定条目注入、大纲位置常驻）正是她想要的，只是被"AI 生成"这道门挡在外面。

付费结构值得单独记：月费 0 元，超过 19 元直接关页面；一次性 98 元买断可以；模型 token 自己付完全接受，因为"这是电费，不是订阅"。

### 3.2 周牧（41，现实主义长篇）— 3/10

同一本书从零开始 5 分。会不会用：否。

他的判断最凝练：**"两句话都在说'写小说'。我要的不是写，是改。"**

他唯一眼睛亮的是不可变修订 + 行级 diff，因为"改到最后不知道哪版是对的"是他六年的痛。但他补了一句关键的：**"它治的是'我改丢了'，不是'我不敢改'"**——diff 长在 History 里，不在按下接受的那一屏，事情发生时它不在场。

设定注入对他为零（他不让 AI 写正文）。AI 审阅"最接近，但还是不对"：他要的不是模型帮他找矛盾，是一张按章排开的事实表——所有关于天气、时间、年龄、称呼的句子排在一起，他自己一眼扫过去。"这是编辑干的活，不是模型干的活。"

他不会搬 22 万字进来。条件按重要性：图形界面导入 docx（门槛）、导出能直接投稿（门槛）、接受前 diff + 接受后撤销（留下的理由）、一张时间线（留下的理由）。

### 3.3 Mira（34，英文自出版奇幻）— 4/10

加系列概念与 diff 之后 6.5 分。会不会用：否，但会装、会拿短篇试、会放进"一年后再看"的书签夹。

她的门槛不是安装（她跑 Immich 和 Home Assistant），是**系列**。一个项目一本书，五本书就是五份互不相通的设定库——"我现在的痛点是'一份不同步'，它给我'五份不同步'"。

她对核心循环的判断最狠：**"我会把这个核心循环绕过去，把它当聊天窗口用。"** 生成、全选、复制、粘到空文档里挑句子。这不是恶意使用，是产品形态与真实需求错配后的自然行为。一旦作者这么做，建立在整章生成之上的 job、usage、快照、审阅全部失效。

她还提了一个此前没人提的缺口：**看不见 AI 读到了什么设定**。四千字符预算被三个次要角色名吃满，最吃重的"代价规则"挤不进去，而作者无法判断是模型没读到还是读到了写错了。"不能审计上下文，就不能信任连续性。"

计费可预测性是她唯一承认的净胜：Sudowrite $25/月加超额，换成软件免费加每月三到六美元 API，"我不需要它更便宜，我需要它不给我惊喜"。

定位句上她给了一句可以直接用的判断：**"真正能让我点进去的那句话，在我读不到的语言里。"** 英文首行是分类（这是哪类软件），中文 H1 是承诺（我的哪一天会变好）。

### 3.4 陈默（52，传统出版，不用 AI）— 2/10

会不会用：否。

他的价值在于说出了别人不好意思说的那句：**如果作者根本不需要 AI，"单作者、本地、数据归属"就不是卖点，是免责声明。** "它不是在说'我很安全'，它是在说'我知道你要做一件让人不放心的事，我尽量让它不那么不放心'。"

但他自己改了口，而且这一次改口是整份模拟里最有价值的一句：**"它把我会要的东西，藏在我绝不会要的东西后面。"** 不可变修订、快照、中文按字检索、能交稿的 DOCX 导出——这四样是手稿管理，跟 AI 一点关系没有，他都要。

他的建议因此非常具体：允许完全不配模型就把整本书写完，模型是插件不是门槛。

他给的目标用户画像也比产品自己的准：三十六岁，工业软件实施顾问，大学在起点写过没签上，现在小平台日更四千、月入三四千，装过 Jellyfin，设定存在 Excel 四张表里（人物、势力、时间线、伏笔），每月愿为 API 花五十到一百但不要订阅。

### 3.5 苏黎（36，出版社签约）— 3/10

会不会用：不会。

她贡献了整份模拟里最锋利的一句行业判断：**"一个写作工具，只要它管的那份正文不是最终稿，它管的就只是草稿。"** 编辑在 Word 里批注，产品明确不做协作，于是正文一旦导出就分家——要么全部重新粘回来，要么从此过期。

她对快照的评价是"唯一让我坐直了的地方"，但立刻指出了落地缺口：**她没法给这一版起名字。** 编辑问"上次那版第三段怎么写的"，她需要的是"2026-10-20 交张编"，不是一串内部哈希。没有命名，14 万字里三十多个修订她一个都指认不出，快照的价值停在半路。

导出接了半条链：DOCX 的中文字体、首行缩进、分页、目录正好是她每次手动做的四样，但**没有 PDF，没有投稿格式预设**，拿回 Word 转 PDF 会重新排版一次，"产品说的确定性导出，到我这一步打了折"。

她给了一个成本很低、价值很高的机会点：如果产品能**导入编辑批注过的 DOCX 并把批注只读定位回正文**，哪怕不做协作，评价从 3 分到 6 分。这不与"不做协作"的非目标冲突——它接收外部反馈，不是多人同时编辑。

### 3.6 竞品产品负责人（Daniel Reyes，虚构）— 对抗性评审

他的第一句话定了全篇性质："我看到这个仓库的第一反应不是威胁，是'它的边际成本是零，我的不是'。"

**客群切分**（按卡在哪一步分，不按人口标签）：产能驱动型只有"既懂技术又撞过额度墙"的 5–8% 会走；工艺驱动型现在绝不会走，0.9.0 补完 diff 后会试用再回来；设定密集型系列作者最该走但进不来；分发受限型（有出版合同、受监管、离线、大量中文作者）结构上只能用它。

**护城河判断**，两条都下调了：

- 快照："不是护城河。我数据模型本来就有 revision，钉在某个 revision set 上是一个 sprint 的活，三到六周。用户也不关心——直到他出事。"它的真实价值是**用架构替代 QA**：没有测试团队的单人项目，只能靠"只留一个读入口"保证不出错。是便宜的保险，不是壕沟。
- 设定即文档："有两到四个季度窗口，窗口内是真差异，窗口后是一句营销文案。"真正卡住他的是安装基数，不是技术。

他给出一个更硬的判断：**真正的护城河是没有账单，也没有信任边界。**"这两点我用功能永远追不上，只能开一条 on-prem 产线，而那会直接拆掉我的毛利率。"

**三个致命弱点**：漏斗在第一步就断且不被当作漏斗问题（"获客成本不是高，是结构上无法规模化"）；责任不可追（进不了任何可报销预算科目，只能进 hobby 预算，这决定天花板而不是功能决定天花板）；看不见用户在哪一步放弃（反馈回路以月计，对手以天计）。

**最刺的一句异议**：0.9.0 的三件事方向都对，但性质错了——"全是在补齐我已经有的东西。补齐后它变成一个功能更少、装起来更难的 Draftwell。这是追赶，不是定位。"以及"它把全部筹码押在第六步，可没人走到第六步"。

**三年后**：在，但不是作为产品在，是作为参考实现加一小群重度用户的自用工具在。"不会长大，也不会死透。"

### 3.7 K（30，后端工程师，硬科幻）— 产品 6 分，迁移净值 +1

会不会用：现在不会。会 star、watch release、提一个 issue 和一个可能很小的 PR。

他是七个角色里唯一给到 6 分的，理由也最特别：**"从零开始建，我从一个已经跑通的工作流上改建，这个差别很大。"** 他承认产品的粒度比 Git 对——"我改一章要提交整本书的 diff，你的修订是单章的"；也承认快照比他的做法强——"我从不打 tag，导出后又改三个字然后忘了是我的常规事故"。

但他提出了一个别人都提不出的问题：**SQLite 和 Git 是两种版本控制，正面冲突。**

`.db` 是页式二进制，`git diff` 只回一句 `Binary files differ`。正文一进数据库，Git 就从历史工具退化成"改一个字存一份十二万字的备份盘"。第二层更隐蔽：他的字数统计、重复句检测、对话与叙述比、专名一致性脚本，全是吃 `*.md` 的，现在要全部重写成 SQL，而且 schema 是内部实现，版本一升他就得跟着改。他的说法很准：**"这不叫格式封闭，这叫格式的所有权从 POSIX 转移给了这个项目。"**

他的解法成本极低：每次保存把当前章镜像到 `content/chNN.md`，或者给 CLI 加 `export --per-chapter --watch`。我核查过，CLI 目前只有 serve / backup / restore / reindex / doctor / migrate / owner / import，**确实没有 export**。这个判断成立。

他还提了一条会改变实现方式的技术意见：**行级 diff 对散文是错的粒度。** 三千字一段就是一个长行，改一个词，整行全红。他自己标注了"这点我可能误判——如果编辑器硬换行到 80 列，行级其实够用"。

我核查了：`frontend/src/features/studio/hooks/useCodeMirrorEditor.ts` 启用了 `EditorView.lineWrapping`，那是软换行，不改变存储内容。所以一段散文在数据里就是一个长行，**他的判断成立**。这直接影响 P0-1 的实现方式——必须按句切分做 LCS，行级实现会把"改一个词"渲染成整段标红，用户会认为这个功能没用。主报告 §8.3 的 P0-2 已据此把工作量从 3–5 人日上调到 5–8 人日。

这是整份模拟里唯一一条"角色的技术判断直接改写了实施计划"的例子，也是为什么 §2 限制六要求核查。

他对界面的意见比"太吵"更精确：左边五组是对的，那是小说写作的固有结构；右边九个标签在 1440 宽、320px 右栏下装不下（九个标签每个约 35px，合计 315px，几乎没有余量）。他真正要的不是减少功能，是**一个安静的状态**——专注模式、侧栏可全隐、Copilot 做成浮层。我核查了前端，没有专注模式实现。

他给了一个很少被注意的成熟度信号：**"未配置的 provider 也能被选中，选中后生成必然失败。"** 他的判断不是"这是个 bug"，是"这是个没人在意的 bug——说明没有一条端到端的验证路径"。他会用提这个 issue 来测维护者的响应速度，两周没人回就不提 PR。

付费结构也值得记：买断 $99 立刻付；$5/月会付但记着退订；$20/月不付，理由是"自托管工具没有持续服务成本，订阅的合理对象是替我跑服务器或替我付 token，你两样都没做"。他还注意到一件反直觉的事：中文 H1 写"无订阅、无按字计费"，他的第一反应不是省钱，是**"那你怎么活"**。

### 4.1 价值评分

| 角色 | 现在 | 条件改善后 | 会不会用 |
|---|---|---|---|
| 林筱（网文日更） | 2 | 6 | 否 |
| 周牧（严肃文学） | 3 | 5 | 否 |
| Mira（英文自出版） | 4 | 6.5 | 否（一年后再看） |
| 陈默（反对派） | 2 | — | 否 |
| 苏黎（出版向） | 3 | 6 | 不会 |
| K（技术型） | 6（迁移净值 +1） | — | 现在不会 |

**七个角色里零个说"是"。** 这个数字要先打折再看：角色设定全部是"已有稳定工作流的中文或英文作者"，天然带迁移成本；而且模拟不会"用着用着就习惯了"。真实作者里存在一批人，装的时候骂，用两周之后就离不开了，这类人在模拟里不存在。

但打折之后仍有一个可用的信号：**没有任何一个角色认为这个产品值得他改变现有工作流**。最低分 2，最高分 6（K 给的是"产品本身"，他的迁移净值只有 +1），条件改善后上限 6.5。没有一个人给到 8 以上。

### 4.2 共识（四个及以上角色独立提到）

| 共识 | 提到的人 | 强度 |
|---|---|---|
| 安装是硬墙 | 林、周、陈、苏（4/7，Mira 与 K 例外） | 强，且有文档事实佐证 |
| 整章替换 + 无 diff + 无撤销 = 不敢按 | 林、周、Mira、陈、苏、K（6/7） | 最强共识 |
| 无导入/无图形导入 = 已有稿子的人进不来 | 林、周、Mira、苏（4/7） | 强 |
| 定位句里的技术词造成门槛（IDE、self-hosted、模型选择） | 七人全部 | 强 |
| 不需要 AI 写正文，要的是"改"或"记" | 林、周、陈、苏、Mira（5/7） | 强，但见 §2 限制二 |

最后一条必须标注：我在角色卡里把五个人都设成了"谨慎对待 AI 正文"，这个共识有相当部分是我设定的产物，不是产品的发现。可用的部分不是"作者不用 AI"，而是**"整章生成"这个粒度与他们的使用方式不匹配**——这一点由 Mira 的"我会绕过核心循环"和林筱的"这是赌博"独立佐证，可信度高于那句笼统的"不用 AI"。

还有两条值得单列，因为它们比"技术词门槛"更具体：

**"无按字计费"这句在打消一个不存在的恐惧。** 林筱、周牧、苏黎、陈默四个人分别说了同一件事：我从来没按字付过费。这句承诺对他们是零信息量，对 Mira 甚至轻微有害——"读起来像 AI 不花钱，我拿到第一张 API 账单时会有落差"。

**产品免费，但收两种税。** 林筱的框架：装机的时间税，和"按错一次就没了两小时"的恐惧税。"这两种税我愿意付的额度是零。"这解释了为什么"免费"不是卖点——对还没进来的人，成本从来不是钱。

### 4.3 真分歧

| 议题 | 一方 | 另一方 | 含义 |
|---|---|---|---|
| 移动端 | 林筱：日更在被窝里，必须有 | 周牧、苏黎：坐书桌，不需要 | 用户群按写作场景分裂，不按题材分裂 |
| 系列管理 | Mira：五本书，刚需 | 周牧、林筱：单本，无关 | 产品当前服务单本，系列是另一个市场 |
| AI 审阅 | 产品已有 | 周牧：要事实表，不要 AI 扫 | "AI 找矛盾"与"我能自己看见矛盾"是两种产品 |
| 交稿格式 | 苏黎：PDF + 投稿预设 | 其他人：完全不关心 | 出版向是一条独立价值链 |
| 定位重心 | 陈默：AI 是门槛，应拆掉 | 产品：AI 是核心 | 见下 |
| 数据格式 | K：正文必须能落成 per-chapter `.md`，否则 grep 与 git diff 全废 | 其余六人：不关心存哪，只要导出能用 | 技术型作者把"文件所有权"当准入门槛，其他人不当 |

五处分歧指向同一件事：**产品在服务一个想象中统一的"长篇作者"，而实际至少存在五个互不兼容的人群**——日更连载、单本打磨、系列经营、出版交稿、技术型自管。它们对"核心循环"的定义都不一样：林筱要快速出稿，周牧要安全改稿，Mira 要跨书一致，苏黎要交得出去，K 要能用脚本吃自己的稿子。

### 4.4 三条合并结论

**结论一：核心循环是单选题，用户需求是多选题。**

整章生成是一个有效场景（空章起稿、卡文硬推），但它被做成了唯一入口。五个角色里四个不用整章生成，其中一个明说会绕过去当聊天窗口。核心循环一旦被绕过，建立在它之上的 job、usage、快照、审阅全部失去意义——这是产品最贵的沉没风险。

**结论二：产品包装成 AI 工具，但最硬的价值是非 AI 的手稿管理。**

三个中文角色都不让 AI 写正文，他们真正要的是伏笔管理、版本对照、交稿格式、全文检索。这些恰好都是产品已有的能力，却全部排在 AI 生成之后。陈默那句话可以当结论用：它把作者会要的东西，藏在作者绝不会要的东西后面。

这与竞品评审的判断交叉印证：竞品认为真正的护城河是"没有账单、没有信任边界"，而不是任何 AI 功能。

**结论三：漏斗断在第一步，而这一步与产品价值无关。**

林筱的原话是"这五条命令，我打在哪"。我核查了 `openwiki/guides/zh/getting-started.md`，实际门槛比 README 更高：要手写 `.env`（写 CORS origin）和 `compose.override.yaml`（YAML 缩进），再执行 `docker compose up -d`。YAML 错一个空格就起不来。这不是模拟推断，是文档事实。

装好之后还有五道坎才能看到第一句 AI 输出：过 Docker、等镜像、翻容器日志找 setup token、建一个空项目、再建一个空章节。竞品评审把这个序列单独数了一遍，因为它决定了一件商业上的事——**内容营销的最后一跳无处可落**。一篇讲"AI 怎么写好打斗场面"的文章，结尾只能写"去 GitHub 装 Docker"，不能写"点这里开始"。获客成本不是高，是结构上无法规模化。

同一份材料还给出一个比功能更硬的判断：**天花板由采购决定，不由功能决定。** 单人维护、无合同、无 SLA、无发票，意味着它进不了任何可报销的预算科目，只能吃 hobby 预算。这条不能靠加功能解决。

### 4.5 模拟给出的最强单一洞察

**如果作者绕过核心循环，这个产品就退化成一个带 AI 的笔记软件。**

反过来说：产品真正的资产（不可变修订、快照、设定派生、中文检索、DOCX 排版）在"绕过 AI"之后依然成立，而 AI 生成在"被绕过"之后一文不值。这个不对称值得写进定位。

## 5. 与既有判断的对照

### 5.1 被证实的

- **接受前 diff 是第一优先级。** 五个角色独立提到，Mira 把它定性为"准入门槛"而非体验优化，与我上一轮 RICE 第一的判断一致，但理由更强。
- **撤销是必要配套。** 无人单独要求撤销而不要求 diff，两者被当作一件事的两面。
- **安装门槛是结构性问题。** 且文档事实比模拟更糟。
- **英文首行需要改。** Mira 的"我读不到那句中文"是最直接的证据。

### 5.2 被修正的四处

**修正一：快照不是护城河。** 我上一轮写"唯一无法被竞品替代的承重卖点"。竞品评审的判断是：数据模型本来就有 revision，钉在 revision set 上是三到六周的活，可复制；用户感知弱，直到他出事。它的真实定位是**用架构替代 QA**——单人项目没有测试团队，只能靠"只留一个读入口"保证一致性。这是保险，不是壕沟。

这个修正不降低它的价值，只降低它的叙事权重。把它当卖点讲，竞品三个月就能复制；把它当"为什么这个产品不会出错"讲，别人抄不走那个约束。

**修正二：部分生成的优先级要上调。** 我上一轮 RICE 给它 0.13，排在第四。模拟显示它不是效率问题，是**核心循环的形态问题**：五个角色里四个不用整章生成。这一项不做，前两项（diff、撤销）只是在优化一条作者本来就想绕开的路。

**修正三：导入不是考古功能。** 我上一轮把导入归为"demo 用途"，四份材料里三份说"没有这条就不用看别的"。对一个已有 20 万字稿子的作者，导入是准入门槛，不是便利功能。

**修正四：托管版不再是中性选项。** 我上一轮列为 P3 的选项 B。竞品评审给了机制解释：做托管版会立刻继承云端产品的成本结构（带宽、存储、支持、SLA），却拿不到对应的融资与获客预算，"会直接拆掉毛利率"。应改为不建议。

### 5.3 新增的五项（我上一轮完全没提）

| 新增项 | 来源 | 为什么之前漏了 |
|---|---|---|
| 图形界面导入（docx/txt，自动分章） | 林、周、Mira、苏 | 我把它当作历史包袱，实际是准入门槛 |
| 修订命名与备注 | 苏黎 | 我只看了"有没有 diff"，没看"能不能指认" |
| 上下文注入可见性 | Mira | 我只审了注入机制的正确性，没审它的可审计性 |
| 完全不用 AI 也能走完全流程 | 陈默 | 我把 AI 当作产品定义的一部分，没当作可选层 |
| 只读导入编辑批注的 DOCX | 苏黎 | 我把它归入"协作"这个非目标，其实它是"接收反馈" |

第三项尤其值得注意：Mira 要的不是改预算、改算法，只是**看见本次注入了哪几条设定**。这是一个只读面板，不需要新机制。

### 5.4 技术核查：四条代码判断，一条错

K 提出了四条可直接核查的判断，我逐条查了仓库：

| 判断 | 核查结果 | 证据 |
|---|---|---|
| "没有 schema_version 或 migration 表，我在这里就停" | **错**。存在 `__drizzle_migrations`，启动时检查待应用迁移 | `server/src/shared/infrastructure/db/pending_migrations.ts` |
| "恢复是 append 新修订，还是把头指针往回拨" | **产品做对了**。restore 生成新修订，`metadata` 记 `restored_from`，`source` 为 `restore`，历史不被改写 | `server/src/contexts/studio/application/revision_service.ts` |
| "只有 CLI backup，没有 CLI export" | **对**。CLI 命令是 serve / backup / restore / reindex / doctor / migrate / owner / import | `server/src/apps/cli/main.ts` |
| "行级 diff 对散文粒度错" | **对，且改变了实施计划**。编辑器启用软换行，一段散文是一个长行 | `frontend/src/features/studio/hooks/useCodeMirrorEditor.ts` |

第一条例子的意义大于结论本身。K 因为一个错误推断就要"在这里停"，而真实用户不会查源码——他们会永远停在那个错误推断上。**产品无法用"实际上是那样"去纠正一个"看起来是那样"的印象。** 这条对可观测性有直接含义：`doctor` 输出里明确列出迁移版本号，成本几乎为零，能消掉一类专家型用户的第一道疑虑。

第二条例子的意义相反。产品在不可变性上做得比角色预期的好，但没有任何界面在讲这件事。K 要恢复三次、数修订数才能确认——那是他的方法，普通作者没有，也不会做。

第三条可以直接变成改进项，见 §6.2。

## 6. 修订后的建议

### 6.1 优先级重排

| 原顺序 | 新顺序 | 变化与理由 |
|---|---|---|
| P0-2 diff before accept | **P0-1** | 不变，但理由升级：不是体验优化，是准入门槛 |
| P0-3 一键撤销 | **P0-2** | 不变，与 diff 是同一件事的两面 |
| P0-4 部分生成 | **P0-3** | 上调。形态问题而非效率问题 |
| — | **P0-4 图形导入** | 新增。四个角色里的三个说"没有这条不用看别的" |
| P0-1 验证轮 | **P0-5（并行）** | 不变，但内容改为"带着假设去验证"（见 §6.3） |

### 6.2 新增的 P1 项

| 项 | 来源 | 成本估计 | 价值 |
|---|---|---|---|
| 修订命名与备注 | 苏黎 | 低。`document_revisions` 已有 `metadata_json` 列，无需迁移；前端加输入，导出时带上 | 让快照从"技术保证"变成"可指认的交付版本" |
| 上下文注入面板（只读） | Mira | 低。注入决策已存在，只需把"本次注入了哪几条"渲染出来 | 让连续性从"相信"变成"可以查" |
| CLI `export --md --per-chapter` | K | 低。复用现有 exporter，十行量级 | 解开数据库与 git 工作流的冲突；同时是给第一个外部贡献者的低门槛入口 |
| `doctor` 输出迁移版本号 | K | 极低 | 消掉专家型用户的第一道疑虑 |
| 系列 / 共享设定库 | Mira、竞品评审 | 中高 | 打开系列作者市场；竞品认为这是产品唯一能赢的窄切口 |
| 无 AI 路径 | 陈默 | 低到中。产品已有 mock provider，需要的是流程上不强制配置 | 让"手稿管理"这条价值线独立成立 |

"无 AI 路径"需要说清楚：不是删掉 AI，是让建项目、写、看修订、检索、导出这条链完全不依赖模型配置。当前 `LLM_PROVIDER` 默认 mock，本地开发无需 key，所以技术上接近可行，缺的是界面与文档上不把 AI 当必经步骤。

### 6.3 十二条可检验假设

这是模拟最有用的产出：把角色的话转成能在访谈里被打分的假设。每条都标注了"若成立则做什么"。

| 编号 | 假设 | 检验方式 | 若成立 |
|---|---|---|---|
| H1 | 非技术作者在安装步骤流失超过七成 | 观察 5 次自装，记录放弃点 | 零终端安装升为 P0 |
| H2 | 已有完稿的作者因无图形导入而放弃 | 访谈首问"你现有稿子多少字、在哪个工具里" | 图形导入保持 P0 |
| H3 | 作者首次接受提案前会主动寻找"改了什么" | 观察首次接受行为，记录是否滚动比对 | 确认 diff 为 P0-1 |
| H4 | 作者会绕过整章生成（复制到外部挑选） | 观察是否出现"生成-复制-粘贴到别处" | 部分生成升为 P0-3 之前 |
| H5 | 系列作者愿意为跨书设定库改变工作流 | 访谈 2 位系列作者 | 系列升 P1 首位 |
| H6 | 作者需要给修订命名才能信任快照 | 访谈中问"你怎么记得哪版交出去了" | 修订命名进 P1 |
| H7 | 作者关心 AI 读到了哪些设定 | 展示注入面板原型，看反应 | 注入面板进 P1 |
| H8 | 存在一批完全不用 AI 的目标作者 | 筛选中加一问"如果这个工具不提供 AI 生成，你还会用吗" | 无 AI 路径进 P1 |
| H9 | 出版向作者愿为投稿格式预设付费 | 访谈 2 位签约作者 | PDF 与模板进 P2 首位 |
| H10 | 英文市场对中文 H1 的三个承诺有同等反应 | 英文母语访谈 2 位 | 英文首行改写 |
| H11 | 用 Git 管稿的技术型作者需要文件级访问才肯迁移 | 访谈 2 位用 git 管稿的作者 | CLI export 进 P1 |
| H12 | 专家型用户因"看不到实现证据"而怀疑成熟度 | 给这类用户看 `doctor` 现有输出，观察是否足够 | 增强 `doctor` 可观测性 |

### 6.4 对 0.9.0 的修订建议

`docs/roadmap.md` 当前的四项（部分生成、接受前 diff、一键撤销、整本逐章确认）方向正确，但缺两项、且缺一个排序理由。

建议改为：

1. 接受前 diff（默认路径，不是可选视图）
2. 一键撤销
3. 部分生成（选区/段落）
4. 图形导入（docx/txt，自动分章）——**新增**
5. 整本逐章确认（保留）
6. 零配置路径的端到端验收——**新增，不是功能**

前五项是功能，第六项是一条验收标准：**不配置任何 provider，从建项目、写、看修订、检索到导出 DOCX，整条链必须走通并且有自动化测试。**

这一条来自陈默，但成本几乎为零：产品默认 provider 就是 mock，本地启动不需要 key，差的只是界面与文档不把 AI 当必经步骤。它验证的不是"能不能不用 AI"，而是"手稿管理这条价值线是否独立成立"——如果成立，产品的市场从"愿意让 AI 参与写作的人"扩大到"想管好长篇稿子的人"，后者的规模大一个量级。

把它当验收标准而不是功能，还有一个好处：它不会膨胀成"AI 开关"这类产品概念，只是确保关闭 AI 之后没有死路。

排序理由写进 roadmap：前两项解决"作者不敢按"，第三、四项解决"作者用不上和进不来"，第六项解决"这份价值是否只对 AI 用户成立"。只做前两项，等于优化一条只有已经进来的人才会走的路。

发布 gate 不变：验证轮仍要先于发布。但验证内容从"十场开放式访谈"改为"十场里至少六场针对 §6.3 的具体假设"。

## 7. 模拟之后该做什么

### 7.1 不要做的三件事

**不要用模拟替换访谈。** §2 的五条限制不是免责套话。模拟能告诉你"这个缺口在不在"，不能告诉你"这个缺口有多痛"。痛感决定优先级，而痛感只能观测。

**不要把"六个角色零个说会用"当成转化率。** 它是一组角色设定的产物，不是样本统计。真实的流失率可能高得多（因为真实用户没有耐心走完流程），也可能低得多（因为真实用户会形成习惯）。

**不要按角色数量投票决定功能。** 四个角色要导入，不代表导入比 diff 更重要——他们都在"进不来"的状态，进不来的人对进来之后的体验没有投票权。

### 7.2 要做的四件事

**第一，用 §6.3 的十条假设重写访谈脚本。** 现有的 `interview-kit.md` 是开放式探索，适合发现未知；现在已经有了一批具体假设，适合做验证式访谈。两者不冲突：前 20 分钟开放式，后 25 分钟针对假设。

**第二，优先招三类人，而不是十个人。** 非技术日更作者（验 H1、H2、H4）、有完稿正在投稿的作者（验 H3、H6、H9）、系列作者（验 H5）。每类两到三人，比十个同质作者有用。

**第三，把 §5.3 的五项新增按成本排序，先做零成本的两项。** 修订命名（已有 metadata_json 列）与上下文注入面板（决策已存在，只需渲染），都不需要新机制。它们的作用不是提升体验，是让模拟里的两个具体假设（H6、H7）在真实用户身上可被检验——先有可看的东西，访谈才有东西可问。

**第四，留一个十行量级的入口给外部贡献者。** K 说得直白：他第一个 PR 会给 CLI 加 `export --md --per-chapter`，因为"解我自己的问题、不碰核心模型、review 成本低"。这类改动的价值不在功能，在**它同时是分发渠道和维护者响应速度的探针**。一个只有单人维护的项目，最缺的不是代码，是第一个愿意提 PR 的人；而第一个 PR 的类型，决定了后面还会不会有人来。

### 7.3 一句留给下一个评审者的话

这次模拟最大的收获不是"发现了五个新功能"，是发现**产品的价值排序和作者的痛感排序不一致**：产品从"生成"开始讲，作者从"别弄丢、别弄错、交得出去"开始想。

如果下一轮评审还是从功能清单入手，会重复这个错。从"作者在哪个时刻会紧张"入手，才会看到那三处断点为什么是断点。
