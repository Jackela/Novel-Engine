# Dark-mode campaign — 2026-09-11

Full-campaign evidence for the dual-theme (light/dark) rollout executed per
`openspec/changes/2026-09-11-dark-mode/`. Decision record: ADR-0010
(accepted); design SSOT: root `DESIGN.md` with the `## Dark theme values`
body appendix; campaign issue: #509. Frontmatter of `DESIGN.md` untouched
(the `@google/design.md` alpha schema has no themes syntax).

## Owner decisions (locked in T0)

- **Tri-state selection**: `system` / `light` / `dark`, persisted under the
  `novel_engine_theme` localStorage key; absent/invalid/unreadable storage
  silently degrades to `system`. `system` resolves with zero JavaScript via
  the CSS media entry; explicit locks are applied before first paint by a
  blocking inline script in `index.html`.
- **Elevated dark**: same material anatomy as light — alpha tiers
  (0.62/0.80/0.45), blur caps (14px/24px), one glass layer per region — with
  deep desaturated canvas fields, bright-source-over-dark radial glows, and
  a brightened teal accent whose `on-accent` flips to dark teal ink.
- **Full dark**: every painted surface follows the dual entry, including
  dark twins inside both fallback override blocks
  (`prefers-reduced-transparency`, `@supports not (backdrop-filter…)`).
- **Whole app**: one token SSOT in `base.css`; no per-surface dark
  stylesheets; ADR-0009 exceptions preserved (opaque editor, no editor
  blur).

## Findings for the main session

- **ThemeSwitch system label does not re-resolve live** — *resolved in the
  T3 series*: discovered by the T3.1 e2e run; the mounted control kept its
  previously rendered `System (dark|light)` label across an OS flip because
  the `matchMedia` listener only set the unchanged stored preference
  (bailing out of the re-render). Fixed by tracking the resolved scheme in
  its own `ThemeSwitch` state refreshed on every system-change event;
  covered by a new unit test (mocked `matchMedia` flip) and the restored
  e2e live-label assertions.
- **Remaining literal `-webkit-backdrop-filter` sites**: 8 prefixed blur
  literals outside `layout.css` still carry byte values
  (`studio-nav.css:23,45`, `inspector.css:8`, `library.css:9,57,72,101`,
  `entry.css:14`). The glass campaign recorded a "Safari var() limitation"
  rationale for keeping literals on prefixed lines; only `layout.css:6`
  was ruled into this ticket. A consistent ruling (switch all to
  `var(--glass-blur[|-strong])` or re-document the limitation in place) is
  left to the main session.
